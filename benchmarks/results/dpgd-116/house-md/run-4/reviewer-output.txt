## Findings

### `[CRITICAL]` main.rs does not exist — no binary entry point

There is no `crates/axiathon-client/src/main.rs`. The story spec explicitly requires it: *"Binary entry point, tracing init, dispatch, exit codes"*. Without it, `axiathon` cannot be built as an executable. The entire command dispatch chain (Cli → Commands → handlers) is dead code with no caller. AC-1 ("axiathon --help must show all command groups") is untestable end-to-end. AC-3 exit code mapping via `std::process::exit()` has no call site.

The crate is a library, not a CLI tool.

### `[CRITICAL]` validate_header_value() exists but is never called — CWE-113 defense is theater

`client.rs:62-74` defines `validate_header_value()` which checks for CRLF/null/length. But `client.rs:81-86` in `get()` injects headers **without ever calling it**. The tests at `siem_client.rs:145-174` verify the validator rejects bad input, but no test verifies that `SiemClient::new()` or `get()` actually calls the validator. A tenant ID of `"evil\r\nX-Injected: yes"` would be injected directly into the HTTP request.

The security control exists on paper but isn't wired. This is worse than not having it — it creates false confidence.

### `[HIGH]` Nightly rustfmt check fails — CI will reject this

`cargo +nightly fmt --all --check` produces diffs in `client.rs:66` and `commands/init.rs:7`. Per the gotchas sidecar: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not."* This will fail CI.

### `[HIGH]` `toml` dependency pinned to `"0.8"` instead of workspace-managed `"0.9"`

`crates/axiathon-client/Cargo.toml:21` uses `toml = "0.8"` as a direct dependency, not workspace-managed. The story spec requires `toml 0.9` in `[workspace.dependencies]`. This violates the workspace dependency management convention — every other dependency correctly uses `workspace = true`. Additionally, `0.8` vs `0.9` is a version mismatch against the spec.

### `[HIGH]` `keyring` dependency entirely missing — no credential storage path

The story spec requires: *"Credential storage: OS keychain via `keyring` crate. Load token at CLI startup in sync context BEFORE entering Tokio runtime to avoid deadlocks."* Neither `keyring = "3"` nor any keychain integration exists anywhere. `config.rs:95-96` returns `None` hardcoded. The `token()` method's doc comment says "Tokens are stored in OS keychain" but that's a lie — there is no keychain code. While the full login implementation is Story 9.1, the `keyring` dependency and the sync-before-async loading pattern are called out explicitly for Story 6.1 as infrastructure.

### `[HIGH]` No TTY auto-detection for output format — AC-4 partially violated

AC-4 states: *"Table default for TTY, JSON for piped output. Use `std::io::IsTerminal`."* `output.rs` has zero TTY detection. `OutputFormatter::new()` takes a format enum directly with no context-aware default. When piped, the operator must manually pass `--format json`. This defeats the scriptability goal. The `IsTerminal` import from `std::io` is nowhere in the codebase.

### `[MEDIUM]` `CliError::ServerError` Display impl leaks inner string — CWE-209

`error.rs:13` defines `#[error("server error")]` for `ServerError(String)`, which means Display shows only "server error" and hides the inner string. Good. BUT the `Unauthorized(String)` variant at `error.rs:19` uses `#[error("unauthorized: insufficient permissions")]` — also hiding the inner value. This is intentional CWE-209 mitigation. However, test `exit_codes.rs:117-128` `cli_error_display_does_not_leak_server_internals` only asserts `!display.is_empty()`. That assertion is **vacuous** — it proves nothing about information leakage. It would pass even if the display showed the full internal error string.

### `[MEDIUM]` `output.rs:85` uses `expect()` in production code

`serde_json::to_string_pretty(&output).expect("JSON serialization failed")` at `output.rs:85` and multiple `expect()` calls in `as_csv` at lines 92-98. The Rust coding rules say *"No `unwrap()` in production code — use `?` or `expect()` with actionable message"*. `expect()` is technically allowed per the rules, but `format_table` returns `String` not `Result<String>`, so there's no way to propagate errors. If serialization fails (unlikely but possible with pathological inputs), this panics in production.

### `[MEDIUM]` `RawConfig` silently ignores unknown fields — no `#[serde(deny_unknown_fields)]`

`config.rs:12-17`: `RawConfig` has no `#[serde(deny_unknown_fields)]`. A config file with `passwrd = "secret"` (typo of `password`) or `srvr_url = "..."` (typo of `server_url`) will silently use defaults instead of warning the operator about the typo. The doc comment even says "Unknown fields are silently ignored" as if this is a feature rather than a foot-gun.

### `[LOW]` `exit_code_success_is_zero` test is a tautology

`exit_codes.rs:14-17` tests `assert_eq!(0u8, 0)`. This literally asserts zero equals zero. It doesn't test any code. It exists solely to pad the test count.

### `[LOW]` `header_value_handles_tabs` test has no assertion

`security.rs:62-68`: The test calls `validate_header_value` with tabs but the result is discarded with `let _ = result`. The comment says "either accept or reject, but must not panic" — but there's no assertion. This is not a test; it's a comment with extra steps.
