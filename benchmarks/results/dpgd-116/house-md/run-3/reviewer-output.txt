### `[HIGH]` Vacuous assertion — `config_returns_error_for_missing_file` proves nothing

```rust
assert!(
    result.is_ok() || result.is_err(),
    "missing config file must not panic"
);
```

`result.is_ok() || result.is_err()` is **always true** for any `Result`. This test cannot fail. It asserts literally nothing. A missing config file could return `Ok(default)` or `Err(...)` — both are accepted. The test name claims it validates behavior for missing files, but it's a no-op.

**File:** `crates/axiathon-client/tests/config_loading.rs:46`

---

### `[HIGH]` `CliError::Config` Display swallows all diagnostic detail

```rust
#[error("configuration error")]
Config(String),
```

The `{0}` payload is never included in the Display output. When `main.rs` does `eprintln!("error: {e}")`, the user sees only `"error: configuration error"` — no indication of *what* went wrong (missing file? bad syntax? type mismatch?). Config errors are not security-sensitive; the user needs to know why their config is broken.

**File:** `crates/axiathon-client/src/error.rs:43`

---

### `[HIGH]` CWE-209 — `NotFound` and `ServerError` leak server response body to user

```rust
#[error("not found: {0}")]
NotFound(String),

#[error("error {0}: {1}")]
ServerError(u16, String),
```

These variants pass `resp.text().await` directly into the Display output. If the server returns stack traces, internal paths, or database errors in 404/5xx response bodies, they flow straight to the user's terminal. The doc comment says "Display impl sanitizes internal details" — it does not.

**Files:** `crates/axiathon-client/src/error.rs:24,27`, `crates/axiathon-client/src/client.rs:96-101`

### `[MEDIUM]` `ClientConfig` silently accepts unknown fields (`#[serde(default)]` without `#[serde(deny_unknown_fields)]`)

A config file with `token = "my-secret"` is silently ignored. While the test acknowledges this, silent acceptance of unknown fields means typos (`servr_url`) are silently ignored too, leading to confusing defaults-instead-of-configured behavior. Given that AC-8 says "Tokens in OS keychain, NOT config file," silently ignoring a `token` field is a missed opportunity to warn the user they're doing it wrong.

**File:** `crates/axiathon-client/src/config.rs:8`

### `[MEDIUM]` Zero timeout accepted — `timeout_secs = 0` passes validation

`timeout_secs` is a `u64` with no lower-bound check. A 0-second timeout would cause immediate request failures. The config validates `server_url` for emptiness but not `timeout_secs` for zero.

**File:** `crates/axiathon-client/src/config.rs:9`

### `[LOW]` `tenant` CLI flag accepts raw `String` — not validated as `TenantId`

The `--tenant` flag is `Option<String>`. `axiathon-core` defines `TenantId` as a validated newtype. While the story says the crate depends on `axiathon-core` for shared types, the tenant value is passed through as a raw string without validation. This defers validation to the server, which is acceptable at this stage but inconsistent with the project's newtype philosophy.

**File:** `crates/axiathon-client/src/cli.rs:35`

## Verdict: **CHANGES_REQUESTED**

The nightly fmt failure is a CI blocker. The vacuous test assertion, swallowed config error detail, and unsanitized server response bodies in error Display are quality and security issues that need to be addressed before merge.

**Mandatory fixes:**
1. Run `cargo +nightly fmt --all` to fix import ordering
2. Replace the vacuous `is_ok() || is_err()` assertion with a real check (should be `is_err()`)
3. Include the payload in `CliError::Config` Display (e.g., `#[error("configuration error: {0}")]`)
4. Sanitize or truncate server response bodies in `NotFound`/`ServerError` Display impls — don't pass raw server responses to users

**Recommended fixes (non-blocking):**
5. Add `timestamp` to JSON ResponseMetadata
6. Fix the wiremock header-absence tests to actually verify absence
7. Add `#[serde(deny_unknown_fields)]` or at minimum warn on unknown config keys
8. Validate `timeout_secs > 0`
