## Findings

### `[HIGH]` 1. No `main.rs` — binary cannot be built

The story requires producing an `axiathon` binary, but there is **no `main.rs`** and no `[[bin]]` section in `Cargo.toml`. The crate is library-only. Without `main.rs`, there is no command dispatch, no exit code mapping via `std::process::exit()`, no tracing initialization, and no actual binary. AC-3 (exit codes applied via `main.rs`), AC-10 (stubs printing to stderr and exiting with code 1), and AC-1 (working `axiathon --help`) are all structurally unmet at the binary level.

**Location:** `crates/axiathon-client/Cargo.toml` — missing `[[bin]]` and `src/main.rs`

---

### `[HIGH]` 2. Nightly `rustfmt` check fails — formatting not compliant

`cargo +nightly fmt --all --check` produces diffs in multiple command files (`alerts.rs`, `config.rs`, `ingest.rs`, `query.rs`, `rules.rs`, `status.rs`, `tenant.rs`). Per `gotchas.md`, nightly fmt must pass before approval.

**Location:** Multiple files under `crates/axiathon-client/src/commands/`

---

### `[HIGH]` 3. `--server` flag missing `env = "AXIATHON_SERVER"` (AC-5 violation)

AC-5 requires `--server` supports `AXIATHON_SERVER` env var. The `cli.rs:22` definition has `hide = true` but no `env = "AXIATHON_SERVER"` attribute. Clap supports `#[arg(env = "AXIATHON_SERVER")]` natively for this purpose.

**Location:** `crates/axiathon-client/src/cli.rs:22`

---

### `[MEDIUM]` 4. Edition mismatch: Cargo.toml says `edition = "2018"`, workspace says `edition = "2024"`

The crate-level `Cargo.toml` declares `edition = "2018"` at line 2, while the workspace declares `edition = "2024"`. The crate-level value **overrides** the workspace value. This causes the `non_fmt_panics` warnings seen in the test build (Rust 2021+ format string behavior) and means the crate doesn't benefit from edition 2024 features. This should be `edition.workspace = true` or removed entirely.

**Location:** `crates/axiathon-client/Cargo.toml:2`

---

### `[MEDIUM]` 5. `RawConfig` silently ignores unknown fields (config safety)

`RawConfig` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. A typo like `api_urll = "..."` or `tokne = "..."` silently compiles and runs with defaults. The test `client_config_does_not_store_tokens` at `security.rs:117-131` demonstrates this — `token = "should-not-be-here"` is silently ignored. The test's `if let Ok(config)` pattern means it passes whether the field is rejected OR silently swallowed, making the assertion vacuous for the silent-swallow case (which is the actual behavior).

**Location:** `crates/axiathon-client/src/config.rs:13-17`

---

### `[MEDIUM]` 6. `CsvImpl::format_rows` silently swallows write errors

At `output.rs:112-113`, CSV write errors are discarded with `let _ = wtr.write_record(...)`. If a write fails (e.g., encoding issue), the output silently truncates without any indication to the operator. This violates the principle of not silently swallowing errors.

**Location:** `crates/axiathon-client/src/output.rs:112-115`

---

### `[MEDIUM]` 7. `completion.rs` returns empty string for unknown shell instead of erroring

At `completion.rs:18`, an unknown shell name silently returns `String::new()` instead of returning a `CliError`. An operator typo like `axiathon completion bsh` would produce empty stdout with exit code 0 — a silent failure.

**Location:** `crates/axiathon-client/src/commands/completion.rs:18`

---

### `[MEDIUM]` 8. `ServerError` Display leaks server response body (CWE-209 risk)

`CliError::ServerError(u16, String)` at `error.rs:18` includes the raw server response body in its Display output: `"server error ({0}): {1}"`. If the server returns internal details (stack traces, SQL errors, internal paths), they pass through to the operator's terminal. The SECURITY doc comment at line 7-8 says not to include internal details, but the implementation does exactly that via the body passthrough.

**Location:** `crates/axiathon-client/src/error.rs:18`

---

### `[MEDIUM]` 9. `toml` version mismatch: workspace declares `0.8`, story spec requires `0.9`

The workspace `Cargo.toml` declares `toml = "0.8"` but the story technical guardrails specify `toml` 0.9. This is a spec compliance gap.

**Location:** Root `Cargo.toml:49`

---

### `[LOW]` 10. Test `exit_code_success_is_zero` is vacuous

At `exit_codes.rs:14`, the test asserts `assert_eq!(0, 0)` — a tautology. It tests nothing about the actual code. A meaningful test would verify that a successful `handle_init()` or similar returns `Ok(())` and that the main loop would map that to exit code 0.

**Location:** `crates/axiathon-client/tests/exit_codes.rs:10-15`

---

### `[LOW]` 11. `output_formatter_trait_has_format_table_method` test body is empty

At `output_format.rs:53-58`, the test declares a local function `assert_formatter` but never calls it. The test passes vacuously.

**Location:** `crates/axiathon-client/tests/output_format.rs:53-58`

### `[LOW]` 12. `bare_trait_objects = "allow"` in crate lints

At `Cargo.toml:31`, `bare_trait_objects = "allow"` is set. The `dyn OutputFormatter` usage at `output.rs:45` uses proper `dyn` syntax already. This lint relaxation is unnecessary and may mask issues elsewhere.

## Verdict: **CHANGES_REQUESTED**

Three HIGH findings block approval:

1. **No `main.rs`** — the binary literally cannot be built. This is the primary deliverable of the story.
2. **Nightly `rustfmt` fails** — per `gotchas.md`, this must pass before approval.
3. **Missing `AXIATHON_SERVER` env var** on `--server` flag — explicit AC-5 requirement.

The MEDIUM findings (silent unknown field handling, CSV error swallowing, empty completion for unknown shell, server body leakage, edition mismatch, toml version) should also be addressed but are not individually blocking.
