# Code Review: Story 6.1 — CLI Framework & Structure

*The gunslinger has studied every line. The Dark Tower demands precision.*

## Observations

### [HIGH] No `main.rs` binary entry point — `crates/axiathon-client/src/main.rs` is missing

The story requires `axiathon-client` to produce the `axiathon` binary. There is no `main.rs`, no `[[bin]]` section in `Cargo.toml`, and no dispatch loop calling command handlers. The crate is library-only. Without `main.rs`, the entire CLI is dead code — there is no binary to ship. This is the central deliverable of Story 6.1.

**Impact:** AC-3 (exit codes via `std::process::exit()`), AC-9 (completion to stdout, instructions to stderr), and the basic user flow are all unverified end-to-end.

### [HIGH] `with_token()` and `with_tenant()` bypass header injection validation — `client.rs:23,35`

The public API has both `with_token()` (unchecked) and `with_token_checked()`. Any caller using the unchecked variant silently bypasses CWE-113 protection. Since there's no `main.rs` wiring, we can't verify which path production code uses. The unchecked methods should be `pub(crate)` at minimum, or removed entirely in favor of the checked variants as the only public API.

### [MEDIUM] `uuid_v4_simple()` and `timestamp_now()` return hardcoded constants — `output.rs:135-150`

`uuid_v4_simple()` returns `00000000-0000-4000-8000-000000000000` every time. `timestamp_now()` returns `1970-01-01T00:00:00Z`. The JSON `ResponseMetadata` per AC-4 should contain a real `request_id` and `timestamp`. The `uuid` crate is already a workspace dependency but not used here. Every JSON response will have identical metadata, making request correlation impossible.

### [MEDIUM] Nightly `rustfmt` check fails — `init.rs`, `config.rs`

`cargo +nightly fmt --all --check` reports formatting diffs. Per the reviewer gotchas sidecar, nightly fmt must pass before approval. This is a gating issue.

### [MEDIUM] `with_env_overrides_from` silently ignores invalid `AXIATHON_TIMEOUT` values — `config.rs:93-98`

If `AXIATHON_TIMEOUT` is set to `"abc"` or `"-5"` or `"0"`, the method silently falls through to the previous value. This is error swallowing — an operator sets an env var expecting behavior and gets no feedback that it was ignored. Should log a warning or return an error.

### [MEDIUM] `sanitize_error_body` uses naive string matching — `client.rs:84-96`

The sanitizer checks for `/usr/`, `/src/`, and `panicked` as substring matches. This is trivially bypassable (e.g., Windows paths `C:\src\`). More importantly, if a legitimate error message from the API contains the substring "panicked" or a URL path like `/src/endpoint`, it will be silently replaced with "internal server error". Consider a more robust approach or at least document the trade-off.

### [MEDIUM] `body[..max_len]` truncation may split multi-byte UTF-8 — `client.rs:92`

`&body[..max_len]` will panic at runtime if byte 200 falls inside a multi-byte UTF-8 character. Use `body.chars().take(n)` or `body.char_indices()` to find a safe boundary.

### [LOW] `with_env_overrides_from` and `with_cli_overrides` are identical implementations — `config.rs:85-120`

These two methods have the exact same body. The semantic distinction (env vs CLI) is good, but the duplication will drift. Consider a shared internal method.

### [LOW] `ClientConfigFile` uses `deny_unknown_fields` but `token` test expects either Ok or Err — `config.rs:7`, `config_loading.rs:196-210`

`#[serde(deny_unknown_fields)]` means `token = "..."` in TOML will be rejected with a deserialization error. The test at line 199 handles both Ok and Err, but the Ok branch can never execute. The test is not vacuous (the Err path exercises real behavior), but the Ok branch is dead code in the test, which is misleading.
