### `[HIGH]` Nightly rustfmt check fails — `config.rs`, `output.rs`, multiple test files

Per the gotchas sidecar: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval." The nightly fmt check shows ~20 formatting differences across `config.rs`, `output.rs`, `cli_structure_tests.rs`, `config_tests.rs`, `exit_code_tests.rs`, `output_format_tests.rs`, and `siem_client_tests.rs`. This will fail CI.

### `[HIGH]` Missing files: `main.rs`, `commands/completion.rs`, `commands/init.rs` — at `crates/axiathon-client/src/`

The story spec explicitly requires these files. AC-9 says `axiathon completion <shell>` must be functional (not a stub), and AC-1 says `init` must be functional. Currently:
- No `main.rs` binary entry point exists — the crate has no `[[bin]]` target and cannot produce the `axiathon` binary
- No `commands/completion.rs` — completion logic is in `lib.rs::generate_completions()` but there's no command handler to wire it
- No `commands/init.rs` — no first-time setup handler exists
- `commands/mod.rs` does not re-export `completion` or `init` modules

Without `main.rs`, the entire CLI is a library with no runnable binary. This is a critical structural gap — AC-3 (exit codes via `std::process::exit()` in main), AC-10 (stub dispatch), and AC-9 (completion to stdout, instructions to stderr) all require `main.rs` to function.

### `[MEDIUM]` `--server` flag missing `env = "AXIATHON_SERVER"` annotation — at `cli.rs:27`

AC-5 requires: "`--server` supports `AXIATHON_SERVER` env var." The test file at `cli_structure_tests.rs:437` even documents this requirement in a comment but then does NOT test it, noting it would require subprocess testing. The actual `cli.rs:27` `--server` field has no `env = "AXIATHON_SERVER"` attribute on the clap arg. This means the env var integration described in AC-5 is simply missing.

### `[MEDIUM]` `validate_tenant_id()` exists but is never called — at `client.rs:51`

`SiemClient::validate_tenant_id()` is a standalone public method that validates against header injection (CWE-113), but it is never invoked during `SiemClient::new()` or anywhere else in the codebase. A malicious tenant ID can be passed to the constructor without validation. The story spec states `toml 0.9` as a key dependency. The workspace `Cargo.toml` declares `toml = "0.8"`. While 0.8 works functionally, this diverges from the documented architecture. Either update the dependency or update the spec.

### `[MEDIUM]` `keyring` dependency missing from workspace and crate — at `Cargo.toml`
