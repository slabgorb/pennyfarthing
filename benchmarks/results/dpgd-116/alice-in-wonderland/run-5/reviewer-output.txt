## Findings

### `[CRITICAL]` No binary entry point — `main.rs` does not exist

The story spec requires: *"The story delivers the `axiathon-client` crate producing the `axiathon` binary"*. AC-3 states: *"`main.rs` catches errors and calls `std::process::exit()`"*.

**There is no `src/main.rs`.** No `[[bin]]` in Cargo.toml. The crate is library-only. You cannot run `axiathon --help`. The data flow trace breaks at dispatch: `Cli::parse()` produces a `Commands` enum variant, but nothing matches on it, nothing calls handlers, nothing calls `process::exit()`.

This means AC-1 ("axiathon --help must show all command groups") is **untestable in practice** — the tests verify the parser in isolation, not the actual binary.

### `[CRITICAL]` Edition mismatch — `edition = "2018"` vs workspace `"2024"` at `Cargo.toml:2`

The workspace declares `edition = "2024"` at root `Cargo.toml:6`. The client crate declares `edition = "2018"`. This is not just cosmetic — edition 2024 changes keyword reservations, import behavior, and other semantics. The crate should inherit from workspace or explicitly match.

### `[CRITICAL]` Nightly fmt check fails at `cli.rs`, test files, and more

Per `gotchas.md`: *"Always include `cargo +nightly fmt --all --check` in the preflight."*

Confirmed failure. Import ordering in `cli.rs:3-4` (crate import before std-lib), long `#[command(after_help = ...)]` attributes that nightly wants wrapped. This is a blocking preflight requirement.

### `[HIGH]` No command dispatch or handler modules — AC-10 unfulfilled

`commands/mod.rs:3` exports only `pub mod completion;`. No other command modules exist. AC-10 requires: *"Unimplemented commands print 'not yet implemented (Story X.Y)' and exit with code 1."*

The `CliError::NotImplemented` variant exists and is tested in isolation (`stub_handlers.rs`), but **no code actually creates these errors in response to commands**. There is no `match cli.command { Commands::Status(_) => Err(CliError::NotImplemented("Story 6.2")) ... }` anywhere.

### `[HIGH]` `bare_trait_objects = "allow"` suppresses Edition 2018→2021 lint at `Cargo.toml:40`

This lint suppression exists solely to make `impl dyn OutputFormatter` at `output.rs:40` compile without warnings. This is a code smell — it's a workaround for using an empty marker trait with static methods on `dyn Trait`, which is unidiomatic Rust. The `OutputFormatter` trait at `output.rs:38` is empty:

```rust
pub trait OutputFormatter {}
```

All methods are `impl dyn OutputFormatter { ... }` static methods. This should be a plain struct or a module-level function set. The empty trait + `impl dyn` pattern is confusing and requires suppressing a workspace lint.

### `[HIGH]` Keyring integration completely absent — AC-8 partially unfulfilled

AC-8 requires: *"Credential storage: OS keychain via `keyring` crate. Load token at CLI startup in sync context BEFORE entering Tokio runtime."*

At `config.rs:67-68`, the only token source is `std::env::var("AXIATHON_API_TOKEN").ok()`. No `keyring` import, no keychain loading code, no `keyring` in `Cargo.toml` dependencies. The comment says "keychain loading is done elsewhere" but there is no "elsewhere."

### `[MEDIUM]` `ConfigFile` silently ignores unknown fields at `config.rs:9-16`

`#[serde(default)]` with no `#[serde(deny_unknown_fields)]` means typos like `servr_url` are silently ignored. The security test at `security.rs:103` acknowledges this ("Rejecting unknown fields is also acceptable") but the test is **vacuous** — it accepts both behaviors, testing nothing. An operator who typos `server_url` as `servr_url` gets the default with zero warning.

### `[MEDIUM]` `ClientConfig.timeout` is parsed but never used at `config.rs:25`, `client.rs:23`

`config.rs:48,54-58` parses and stores timeout. `client.rs:23` creates `reqwest::Client::new()` with default timeouts. The stored timeout value is never applied to the HTTP client. Dead code that gives false confidence.

### `[MEDIUM]` `with_token()` bypasses CRLF validation at `client.rs:42-46`

Two token setters exist: `with_token()` (no validation, line 43) and `with_token_validated()` (CRLF check, line 49). Same for tenant. The non-validated versions are `#[must_use]` but have no safety gate. Nothing prevents a caller from using the unsafe path. The validated methods should be the only public API, or `with_token` should call validation internally.

### `[LOW]` `output.rs:82` uses `.expect()` for JSON serialization

```rust
serde_json::to_string_pretty(&output).expect("JSON serialization should not fail")
```

Per rust.md: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect` message is explanatory but not actionable. Same pattern at lines 88-89, 91, 94, 95-96 for CSV. Since these serialize from known-good in-memory data, panics are theoretically impossible, but 5 `expect()`s in one function is aggressive.

### `[VERIFIED]` Exit code mapping is correct and thoroughly tested

`error.rs:35-41` — Auth→3, Authz→4, everything else→1. `exit_codes.rs` has 13 tests including distinctness checks between auth/authz/generic. Solid.

### `[VERIFIED]` CRLF header injection prevention works

`client.rs:49-83` — Both `with_token_validated()` and `with_tenant_validated()` reject `\r` and `\n`. Tests at `security.rs:48-66` confirm.

### `[VERIFIED]` CWE-209 error sanitization is correct

`error.rs:47` — `ServerError(_)` Display outputs generic message, not the inner string. Test at `security.rs:18` confirms internal IPs/ports don't leak.

### `[VERIFIED]` Token never loaded from config file
