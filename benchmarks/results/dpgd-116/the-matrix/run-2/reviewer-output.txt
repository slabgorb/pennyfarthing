## Review Observations

### [CRITICAL] `panic!()` in production code — `generate_completion()` at `commands/completion.rs:26`

```rust
other => panic!("unsupported shell: {other}"),
```

The `generate_completion()` function panics on unsupported shell names. This is production code reachable from user input (`axiathon completion garbage`). The Rust coding rules explicitly state: **"No `unwrap()` in production code — use `?` or `expect()` with actionable message."** A `panic!` is worse than `unwrap()`. This should return `Result<String, CliError>` and map the unknown shell to `CliError::General`.

### [HIGH] Missing `logout` and `tui` command groups — AC-1 violation at `cli.rs:47-87`

AC-1 requires `axiathon --help` to show `login`/`logout` and `tui`. The `Commands` enum has neither a `Logout` nor a `Tui` variant. The tests (`help_contains_all_command_groups` at `cli_structure.rs:77`) don't check for `logout` or `tui` either, which masks this gap. These are explicitly listed in the AC:

> "query, rules, alerts, ingest, config, status, tenant, **login/logout**, **tui**, completion, init"

### [HIGH] `ServerError` Display leaks raw server message — CWE-209 at `error.rs:26`

```rust
#[error("server error ({0})")]
ServerError(u16, String),
```

The `Display` impl echoes the second field verbatim. The test `cli_error_display_does_not_leak_internal_paths` at `security.rs:15` is **vacuous** — it only asserts `!display.is_empty()`, which proves nothing about information leakage. If the server responds with `"Internal: /var/lib/axiathon/db panicked at query.rs:42"`, that entire string appears in the user-facing error message. The error type's own doc comment says `"Display impls must not leak internal paths"`, but the implementation contradicts this.

### [HIGH] `expect()` in `OutputFormatter` production code — `output.rs:57,62-67`


Five `expect()` calls in production formatting code. While these are arguably infallible, the project rules say to use `?` in production. If `format_table` returned `Result<String, CliError>`, these could propagate cleanly.
