## Findings

### 1. [HIGH] `cargo +nightly fmt --all --check` fails — `completion.rs:37`, `init.rs:18-19`

Per the reviewer gotchas: *"Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval — don't let it slip to post-merge."* Two files have nightly-only formatting differences. This is a blocking issue per project conventions.

### 2. [HIGH] Silent JSON deserialization swallowing in `SiemClient::get()` at `client.rs:90`

```rust
let body = response
    .json::<serde_json::Value>()
    .await
    .unwrap_or(serde_json::Value::Null);
```

If the server returns a 2xx response with a body that isn't valid JSON (or is empty), this silently returns `Value::Null` instead of reporting the error. This is exactly the kind of silent error swallowing that causes debugging nightmares in production. A corrupt response from the server will appear as a successful call with null data. Should return an `Err(CliError::ServerError(...))` for deserialization failures.

### 3. [MEDIUM] `OutputFormat` enum is dead code at `cli.rs:110-116`

The `OutputFormat` enum derives `ValueEnum` but is never used anywhere in the codebase. The `--format` flag at `cli.rs:19` uses `value_parser = ["table", "json", "csv"]` (raw strings) instead of the type-safe enum. Either use the enum or remove it — dead code shipped to production is confusing.

### 4. [MEDIUM] `CliError::ConfigError` misused as catch-all in `output.rs`

Throughout `output.rs`, serialization and CSV writing errors are mapped to `CliError::ConfigError`:
- `output.rs:15`: `serde_json::to_value` error → `ConfigError`
- `output.rs:192`: `csv::Writer::write_record` error → `ConfigError`
- `output.rs:156`: `serde_json::to_string_pretty` error → `ConfigError`

These are formatting/serialization errors, not configuration errors. This misclassifies the error semantics. A new variant like `FormatError` or `OutputError` would be more honest, or at least use `ServerError` which is the generic catch-all.

### 5. [MEDIUM] Vacuous test: `piped_output_defaults_to_json` at `output_format.rs:242-263`

```rust
if !stdout.is_empty() {
    let is_json = serde_json::from_str::<serde_json::Value>(&stdout).is_ok();
    assert!(is_json, ...);
}
```

Since `status` is a stub that returns `Err(NotImplemented(...))`, stdout is **always empty**, so the assertion body **never executes**. This test passes vacuously and does not actually verify AC-4's TTY auto-detection behavior. The test name promises something it doesn't deliver.

### 6. [MEDIUM] `toml` crate version mismatch with spec — `Cargo.toml:62`

The story technical guardrails specify `toml 0.9`, but the workspace declares `toml = "0.8"`. Minor semver difference, but deviates from the spec.

### 7. [LOW] `From<AxiathonError>` catch-all maps everything to `ServerError` at `error.rs:69`

```rust
other => Self::ServerError(other.to_string()),
```

`AxiathonError::Io`, `::Parse`, `::Json`, `::Validation`, `::Storage`, `::Internal` all become `ServerError`. An `Io` error from the core crate is not a "server error" — it's semantically misleading. Not blocking, but worth noting for future stories.
