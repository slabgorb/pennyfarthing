### [HIGH] `Mutex` used inside async context at `src/middleware/rate_limit.rs:8,37`

`std::sync::Mutex` is held across no `.await` points here (just the `check` method), so it won't block the runtime *today*. However, this is inside an async middleware path, and a `std::sync::Mutex` that gets contended under high concurrency will spin-wait and block the Tokio thread pool. The correct choice for async rate limiting is `tokio::sync::Mutex` or, better, a lock-free approach. Under load testing this will become a bottleneck. Given the AC says "configurable per-tenant limits" and production will face concurrent requests, this is a correctness-under-load concern.

## Hard Questions

- **What happens with `\r\n` in Authorization header?** `to_str()` rejects non-visible ASCII, so binary attacks return `Err` → 401. **OK.**
- **What if rate limiter `Mutex` is poisoned?** `expect()` will panic, crashing the request handler. In production this would crash the thread. Should use `.lock().unwrap_or_else(|e| e.into_inner())` for resilience, or at minimum return 500.
- **What if two requests arrive with the same tenant at the exact Instant boundary?** One resets the window, the other may see a stale bucket. The `Mutex` serializes access, so this is safe but the window reset is not sliding — it's a fixed window that can allow 2x burst at window boundaries. The AC says "sliding window" is not required, but the doc comment at `rate_limit.rs:14` says "sliding window counter" which is inaccurate.
- **Memory growth:** The `HashMap<String, TenantBucket>` in the rate limiter grows unboundedly. Every unique tenant ID adds an entry that is never cleaned up. Under a tenant-ID-guessing attack, this is unbounded memory growth (DoS vector).
