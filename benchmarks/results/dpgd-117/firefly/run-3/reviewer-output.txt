## Findings

### CRITICAL

**[CRITICAL] ApiResponse envelope schema contradicts story AC and test expectations** — `crates/axiathon-core/src/types.rs:220-228`

The `ApiResponse<T>` struct has `error: Option<ApiError>` (singular) and uses `skip_serializing_if = "Option::is_none"` on ALL three fields (`data`, `error`, `meta`). The story AC and tests demand:
- `meta` **always present** with `request_id`, `timestamp`, `trace_id`
- `errors` as an **always-present array** (empty on success)
- `data` as null on error (not absent)

The current type:
1. Uses `error` (singular) not `errors` (array) — tests at lines 152, 177, 694, 729, 918, 994, 1025, 1037 all assert `json["errors"].is_array()`
2. Skips serializing `meta` when None — tests at lines 137, 173, 919, 1024 assert `meta` is always present
3. Skips serializing `data` when None — tests at line 170 assert `data` is null (present but null), not absent
4. `ApiMeta` has `total/limit/offset` fields but is missing `request_id`, `timestamp`, `trace_id` which every test asserts

This is a **schema mismatch between core types and the API contract**. The implementation will fail every envelope test.

**[CRITICAL] ApiMeta missing required fields** — `crates/axiathon-core/src/types.rs:296-304`

`ApiMeta` has `total`, `limit`, `offset` (pagination fields). The AC requires `request_id` (UUID), `timestamp` (ISO 8601), and `trace_id` (String). These three fields are entirely absent from the struct. Every meta-related test will fail.

**[HIGH] ApiError struct does not match RFC 9457 Problem Details** — `crates/axiathon-core/src/types.rs:280-287`

The `ApiError` has fields `code`, `message`, `trace_id`, `details`. RFC 9457 requires `type` (URI), `title`, `status` (integer). Tests at lines 251-262 assert `error["type"]`, `error["title"]`, `error["status"]` — none of which exist on the current `ApiError` struct. The error shape is fundamentally wrong for the AC.

**[HIGH] Client-supplied X-Request-Id accepted without validation** — test at line 614-633

The test `client_provided_request_id_is_honored` passes `"client-supplied-request-id-12345"` and expects it echoed verbatim. This is a **log injection / header injection vector** (CWE-117). The implementation must validate/sanitize client-supplied request IDs (length limit, character whitelist) before using them in tracing spans and log output. No test enforces sanitization of malicious request IDs (e.g., containing newlines, very long strings, or control characters).

### MEDIUM

**[MEDIUM] Rate limiting tests may be flaky** — `crates/axiathon-server/tests/rest_api_foundation.rs:640-699`

Three rate limit tests send up to 200 sequential requests using `app().oneshot()`. Each call creates a fresh `Router` via `app()` — if the rate limiter state lives inside `AppState` and `app()` creates a new state each time, the rate limiter resets on every call and 429 is never triggered. The test helpers call `app()` per-request (line 40). This design makes rate limit tests structurally unfalsifiable unless `app()` returns a shared-state router. The test should build one router and call `.clone()` on it.

**[MEDIUM] Missing test: oversized request body handling** — No test exists for payloads exceeding reasonable limits. The AC mentions rate limiting is configurable but there's no test for body size limits. Without Axum's `DefaultBodyLimit`, an attacker could send multi-GB payloads.

**[MEDIUM] `send_request` fallback silently swallows non-JSON responses** — `crates/axiathon-server/tests/rest_api_foundation.rs:48-49`

When `serde_json::from_slice` fails, the helper wraps the body in `Value::String(...)`. This means a test could pass on a non-JSON response that happens to contain the string `"errors"` as a substring. The helper should `panic!` on non-JSON for tests that require JSON, or at minimum the envelope tests should assert the raw content-type first.
